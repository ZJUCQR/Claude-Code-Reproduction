    模型流到 渲染管线（深潜审计版）

    2)核心论点

    01 页的核心不是“把文本打印出来”，而是把模型流稳定投影成用户可见状态：

    1. delta 事件必须先装配，再渲染；
    2. text/thinking/tool_use/refusal/stop_reason 各自有不同显示语义；
    3. live/static/transcript 模式改变视图，不改变底层消息语义；
    4. 不完整 stream、abort、fallback 都要有可解释 UI 终态。

    3)运行时状态所有权

    状态类别 所有者 关键函数/字段 说明
    流事件装配态 claude.ts + messages.ts stream parser / handleMessageFromStream 增量事件到消息状态
    内容规范化态 messages.ts normalizeContentFromAPI / normalizeMessagesForAPI 最终 API/REPL-safe 内容
    refusal/stop 态 api/errors.ts getErrorMessageIfRefusal refusal stop_reason 的用户可见投影
    REPL streaming 态 REPL.tsx streamingText / streamingThinking / streamingToolUses 当前轮实时投影状态
    渲染策略态 Messages.tsx static vs live rendering decision overlay / transcript / static row 分支
    查找缓存态 messages.ts buildMessageLookups 渲染与 completion 相关 lookup

    4)端到端流程

    1. claude.ts 解析 content_block_start/delta/stop 与 message_delta/message_stop；
    2. handleMessageFromStream 将 text/thinking/tool_use 等块增量并入状态；
    3. REPL.tsx 维护 streamingText / streamingThinking / streamingToolUses；
    4. Messages.tsx 根据 live/static/transcript 选择渲染策略；
    5. 最终 assistant message 完成后，规范化结果进入消息历史；
    6. refusal/max_output/context-window/abort/fallback 则进入对应终态展示路径。

    5)守卫与决策矩阵

    Guard 条件 动作 结果
    block start guard text / thinking / tool_use 切换对应 streaming state 显示语义正确
    delta guard text_delta / thinking_delta / input_json_delta 追加到对应累积器 增量装配稳定
    stop_reason guard refusal / max_tokens / context_window_exceeded 转可解释错误/终态 防静默终止
    incomplete stream guard 无有效 assistant 输出 进入 fallback 保持可用性
    render mode guard live / static / transcript 选择 overlay 或静态行 UX 一致
    memoization guard 消息稳定但 streaming state 变化 合理复用/重渲染 防 key churn
    abort guard 用户中断 结束当前 streaming overlay 防假挂起

    6)失败、恢复与降级

    6.1 不完整

    • 没有完整 assistant 内容块或 stop_reason；
    • 进入 fallback，而不是把残缺响应当成功。

    6.2

    • getErrorMessageIfRefusal 转为用户可读错误；
    • 不把 stop_reason 仅保留为底层字段。

    6.3

    • 用户 abort 与 SDK timeout 分流；
    • UI 终态需要能解释“谁终止了这轮流”。

    6.4 退化

    • transcript mode 下抑制部分 live chatter；
    • 即使 overlay 缺失，也必须保留最终消息历史与错误终态。

    7)不变量

    1. delta 事件必须先装配，后渲染。
    2. streaming overlay 不能替代最终消息历史。
    3. live/static/transcript 只能改变投影视图，不能改变消息语义。
    4. refusal/max_output/context-window 终态必须可解释。
    5. incomplete stream 不得伪装成成功轮次。
    6. 渲染 memoization 不得造成状态冻结或重复 remount。

    8)跨模块契约

    • 对 02：01 不定义 request ledger，只消费已关联好的控制/内容事件。
    • 对 03：01 消费 transport 提供的有序事件流，不处理 replay 细节。
    • 对 04：01 只渲染 tool progress/final result，不管理执行 admission。
    • 对 query/tool 主链：01 是投影视图，不改变业务语义。

    9)工程约束与演进指引

    新增 stream 事件或 UI 状态时必须验证：

    1. 是否进入统一装配器；
    2. 是否区分 overlay 状态与 final message 状态；
    3. 是否在 transcript/live 模式下都可解释；
    4. 是否会把 fallback/abort/refusal 混成同一终态。

    建议回归：

    • content_block_start/delta/stop；
    • thinking/text/tool_use 三态；
    • refusal/max_tokens/context-window；
    • live/static/transcript 渲染差异；
    • incomplete stream 与 abort UI 终态。
