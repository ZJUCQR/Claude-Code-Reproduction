    权限决策与安全防护（深潜审计版）

    1)范围与证据边界

    本页覆盖“Hook 如何进入 Tool permission 决策链”与“安全门如何约束 hook 生效”，证据范围：

    • src/services/tools/toolHooks.ts
    • src/services/tools/toolExecution.ts
    • src/utils/hooks.ts
    • src/utils/permissions/permissions.ts
    • src/utils/hooks/ssrfGuard.ts

    不覆盖：

    • hook 配置/匹配/排序（见 01）；
    • exec 协议细节（见 02）；
    • Session/File hook 的 watcher/progress UX（见 04）。

    2)核心论点

    权限桥接层的核心不是“让 hook 参与决策”，而是保证 hook 参与后系统仍保持安全边界：

    1. hook allow 只是建议，不是越权放行；
    2. deny/ask 与 requiresUserInteraction 仍需在统一 merge 点收敛；
    3. updatedInput 与 decision 必须同源前进；
    4. trust gate、HTTP allowlist、SSRF 与 managed-only 等护栏是全局有效的。

    3)运行时状态所有权

    状态类别 所有者 关键函数 说明
    hook permission 态 toolHooks.ts runPreToolUseHooks PreToolUse 产出 allow/deny/ask/passthrough
    merge 决策态 toolHooks.ts resolveHookPermissionDecision hook + rule + canUseTool 合成
    post/failure hook 态 toolHooks.ts runPostToolUseHooks / runPostToolUseFailureHooks 执行后补充上下文/失败处理
    tool 调用消费态 toolExecution.ts runToolUse / checkPermissionsAndCallTool 消费 hook 决策并决定执行/拒绝
    规则权限态 permissions.ts rule-based permissions 明确 deny/ask 规则的事实源
    安全护栏态 hooks.ts + ssrfGuard.ts trust gate / HTTP allowlist / SSRF 约束 hook 可执行面

    4)端到端流程

    1. runPreToolUseHooks 执行并产出 hookPermissionResult 与可能的 updatedInput；
    2. resolveHookPermissionDecision 把 hook 结果与 rule-based permissions、canUseTool 合成；
    3. runToolUse / checkPermissionsAndCallTool 消费最终 permissionDecision；
    4. allow 进入工具调用，ask 进入交互确认，deny 直接拒绝；
    5. 执行成功后 runPostToolUseHooks，失败后 runPostToolUseFailureHooks；
    6. PermissionDenied 等补充 hooks 可提供 retry/additional context 等后续语义。
    // src/services/tools/toolHooks.ts
if (hookPermissionResult?.behavior === 'allow') {
  const ruleCheck = await checkRuleBasedPermissions(tool, hookInput, toolUseContext)
  if (ruleCheck?.behavior === 'deny') {
    return { decision: ruleCheck, input: hookInput }
  }
  ...
}

    5)守卫与决策矩阵

    Guard 条件 动作 结果
    hook allow merge guard hook 返回 allow 仍执行规则检查与 canUseTool 防越权放行
    deny guard rule 或 hook 最终 deny 拒绝执行 tool 保持安全边界
    ask guard rule/hook 要求 ask 打开交互确认 保留用户裁决
    passthrough guard 仅 updatedInput 无决策 继续正常 permission 流 输入可变，权限不变
    interaction-required guard tool 需用户交互 即使 allow 也需 canUseTool 防静默操作高风险工具
    trust gate 未信任工作区 阻止 hook 执行 全局安全门
    HTTP/SSRF guard HTTP hook 出网 allowlist + ssrfGuard 防任意网络访问

    6)失败、恢复与降级

    6.1 执行异常

    • hook 执行异常收敛为 hook_error / non-blocking 或拒绝分支；
    • 不让异常绕过统一 permission merge 点。

    6.2 与规则冲突

    • allow 后仍走 rule check；
    • deny/ask 可覆盖 allow，确保策略层优先。

    6.3 分支

    • hook 只修改输入、不改决策时，保留正常 permission 流；
    • 防止输入更新与决策脱节。

    6.4

    • executePermissionDeniedHooks 可返回 retry 语义；
    • 上层可提示模型重新尝试，不直接静默吞掉失败。

    7)不变量

    1. 最终权限判定必须可追踪（decision + reason）。
    2. hook allow 不能绕过显式 deny/ask。
    3. updatedInput 与 decision 必须同源推进。
    4. deny 一旦成立，不再进入 tool call。
    5. trust gate 必须在 hook 层统一生效。
    6. HTTP hook 的网络访问必须受 allowlist/SSRF 约束。

    8)跨模块契约

    • 对 01：03 不定义 matcher 选择，只消费命中 hooks。
    • 对 02：03 消费统一 HookResult，不关心具体执行协议实现。
    • 对 04：03 的 deny/retry/additionalContext 需要被 UI/summary 正确呈现。
    • 对权限系统：03 是 hook 与规则层的 merge 点，不是替代层。

    9)工程约束与演进指引

    新增 permission hook 语义时必须验证：

    1. 是否破坏 allow/deny/ask 的三分结构；
    2. 是否允许 hook 旁路规则层；
    3. 是否让 updatedInput 与 decision 脱节；
    4. 是否破坏 requiresUserInteraction 与 trust/HTTP 安全门。

    建议回归：

    • PreToolUse allow/deny/ask/passthrough；
    • rule deny 覆盖 hook allow；
    • PermissionDenied retry；
    • interaction-required 工具；
    • HTTP allowlist + SSRF 路径。
