    AgentLoop 与 Tool：单工具执行、权限与错误封装（深潜审计版）

    1) Scope 与 Evidence Boundary

    本页只覆盖 src/services/tools/toolExecution.ts 的单工具事务闭环：

    • runToolUse：入口与总兜底；
    • streamedCheckPermissionsAndCallTool：流式桥接；
    • checkPermissionsAndCallTool：校验、hooks、权限、调用、后处理。

    不覆盖：

    • 批次并发调度（见 03）；
    • Query 级恢复状态机（见 02）；
    • stop hooks 总收尾（见 05）。

    2) Core Thesis

    toolExecution.ts 的价值不在“把 tool.call 跑通”，而在把工具调用转译成可审计协议事务：

    1) 输入结构必须可验证； 2) 权限决策必须可解释； 3) 执行失败必须可消息化； 4) hook 可干预但不能破坏 tool_use_id 对偶关系。

    核心入口证据：

    export async function* runToolUse(
  toolUse: ToolUseBlock,
  assistantMessage: AssistantMessage,
  canUseTool: CanUseToolFn,
  toolUseContext: ToolUseContext,
): AsyncGenerator<MessageUpdateLazy, void> {
  const toolName = toolUse.name
  let tool = findToolByName(toolUseContext.options.tools, toolName)
  ...
}

    3) Runtime State Ownership

    3.1 runToolUse：工具识别与外围分支

    职责： - 在可用工具集中解析工具； - fallback 到 base tools 的 alias 兼容路径； - unknown tool / 预中断分支直接消息化返回。

    3.2 streamedCheckPermissionsAndCallTool：统一输出通道

    职责： - 把 progress 事件与最终结果合并为同一 AsyncIterable； - 避免上层再拼接两路流。

    核心片段：

    const stream = new Stream<MessageUpdateLazy>()
checkPermissionsAndCallTool(..., progress => {
  stream.enqueue({
    message: createProgressMessage({
      toolUseID: progress.toolUseID,
      parentToolUseID: toolUseID,
      data: progress.data,
    }),
  })
})
  .then(results => {
    for (const result of results) {
      stream.enqueue(result)
    }
  })
  .catch(error => {
    stream.error(error)
  })
  .finally(() => {
    stream.done()
  })

    3.3 checkPermissionsAndCallTool：事务主控

    职责： - schema 与语义校验； - pre/post hooks； - 权限决策归一； - tool.call 执行与结果封装； - 失败路径 + failure hooks。

    4) End-to-end Flow（单工具事务）

    1. 工具发现与 alias 回退。
    2. schema 校验（safeParse）。
    3. validateInput 语义校验。
    4. 预启动 bash classifier（并行化权限判断）。
    5. 执行 PreToolUse hooks（可改输入、可 stop）。
    6. 解析最终权限决策。
    7. 权限拒绝：构造 error tool_result 并返回。
    8. 权限允许：执行 tool.call。
    9. map result block -> 存储处理 -> 构造 user message。
    10. 执行 PostToolUse hooks。
    11. 成功返回结果列表。
    12. 失败 catch：执行 PostToolUseFailure hooks 并返回错误结果。

    5) Guard / Decision Matrix

    Guard 条件 动作 输出语义
    unknown tool tool 与 alias 都未命中 直接返回错误 <tool_use_error>No such tool
    pre-abort abortController.signal.aborted 返回 cancel result tool_result is_error=true
    schema fail safeParse 失败 返回 InputValidationError error tool_result
    validate fail validateInput.result=false 返回业务错误 error tool_result
    prehook stop hook 发 stop 立即返回 stop result error tool_result
    permission deny behavior !== allow 返回拒绝语义+可选内容块 error tool_result (+attachments)
    call throw tool.call 抛错 失败 hooks + 错误封装 error tool_result
    posthook prevent shouldPreventContinuation 附加 stopped_continuation attachment + result

    6) Failure / Recovery / Degradation

    6.1 工具不存在：兼容路径后仍失败才报错

    let tool = findToolByName(toolUseContext.options.tools, toolName)
if (!tool) {
  const fallbackTool = findToolByName(getAllBaseTools(), toolName)
  if (fallbackTool && fallbackTool.aliases?.includes(toolName)) {
    tool = fallbackTool
  }
}
...
if (!tool) {
  yield {
    message: createUserMessage({
      content: [
        {
          type: 'tool_result',
          content: `<tool_use_error>Error: No such tool available: ${toolName}</tool_use_error>`,
          is_error: true,
          tool_use_id: toolUse.id,
        },
      ],
    }),
  }
  return
}

    语义： - 先兼容，后失败； - 失败路径可被模型继续消费。

    6.2 输入防御：双层校验 + 防御性剥离

    schema 校验失败

    const parsedInput = tool.inputSchema.safeParse(input)
if (!parsedInput.success) {
  let errorContent = formatZodValidationError(tool.name, parsedInput.error)
  ...
  return [{ message: createUserMessage({ ... is_error: true ... }) }]
}

    语义校验失败

    const isValidCall = await tool.validateInput?.(parsedInput.data, toolUseContext)
if (isValidCall?.result === false) {
  return [{ message: createUserMessage({ ... is_error: true ... }) }]
}

    defense-in-depth 清洗

    let processedInput = parsedInput.data
if (
  tool.name === BASH_TOOL_NAME &&
  processedInput &&
  typeof processedInput === 'object' &&
  '_simulatedSedEdit' in processedInput
) {
  const { _simulatedSedEdit: _, ...rest } = processedInput as ...
  processedInput = rest as typeof processedInput

    语义：即便 schema 应该拦住，也在执行前再剥离一次内部字段。

    6.3 PreToolUse hooks：可阻断事务

    for await (const result of runPreToolUseHooks(...)) {
  switch (result.type) {
    case 'hookPermissionResult':
      hookPermissionResult = result.hookPermissionResult
      break
    case 'hookUpdatedInput':
      processedInput = result.updatedInput
      break
    case 'preventContinuation':
      shouldPreventContinuation = result.shouldPreventContinuation
      break
    case 'stop':
      resultingMessages.push({
        message: createUserMessage({
          content: [createToolResultStopMessage(toolUseID)],
          toolUseResult: `Error: ${stopReason}`,
          sourceToolAssistantUUID: assistantMessage.uuid,
        }),
      })
      return resultingMessages
  }
}

    语义：PreToolUse 不是“日志 hook”，而是可改输入、可提前停机的控制层。

    6.4 权限拒绝：拒绝也是协议内结果

    if (permissionDecision.behavior !== 'allow') {
  const messageContent: ContentBlockParam[] = [
    {

      is_error: true,

    语义：deny 不抛异常，而是生成带 tool_use_id 的标准错误结果。

    const result = await tool.call(callInput, {...}, canUseTool, assistantMessage, progress => {...})
...
const mappedToolResultBlock = tool.mapToolResultToToolResultBlockParam(
  result.data,
  toolUseID,
)
...

  ? await processPreMappedToolResultBlock(...)
  : await processToolResultBlock(tool, toolUseResult, toolUseID)

    语义： - tool.call 不是最终输出，后面还有映射与存储层处理； - 输出语义仍由统一格式器收敛。

    6.6 调用失败：failure hooks + 错误封装

    } catch (error) {
  ...
  const hookMessages: MessageUpdateLazy<AttachmentMessage | ProgressMessage<HookProgress>>[] = []
  for await (const hookResult of runPostToolUseFailureHooks(...)) {
    hookMessages.push(hookResult)
  }

  return [
    {
      message: createUserMessage({
        content: [
          {
            type: 'tool_result',
            content,
            is_error: true,
            tool_use_id: toolUseID,
          },
        ],
      }),
    },
    ...hookMessages,
  ]
}

    语义：失败后也维持协议完整，并运行 failure hooks 做收尾增强。

    7) Invariants

    1. 每次 runToolUse 最终都必须返回可消费消息（成功或错误）。
    2. tool_use_id 必须贯穿到最终 tool_result。
    3. 权限拒绝必须走协议内消息，不能抛穿 query loop。
    4. hook 改写输入不得破坏 tool.call 参数一致性。
    5. toolDecisions 必须在 finally 清理，避免跨调用污染。
    6. failure hooks 即使失败也不能让主错误消息丢失。
    7. alias 只用于兼容，不得覆盖主工具语义。
    8. 输入校验失败必须在调用前终止，禁止带病执行。

    8) Cross-module Contracts

    • 上游（query/orchestration/executor）只依赖 MessageUpdateLazy 协议。
    • 下游工具必须遵循 Tool 合约：inputSchema、call、mapToolResultToToolResultBlockParam。
    • 权限系统通过 resolveHookPermissionDecision 汇总 hook 与 canUseTool 决策，工具层不自建分裂权限路径。

    9) Engineering Constraints / Evolution Guidance

    新增工具或新权限策略时必须验证：

    1. schema 与 validateInput 覆盖边界输入；
    2. deny 路径可完整生成 tool_result；
    3. failure hooks 不会吞掉主错误；
    4. contentBlocks/imagePasteIds 在 allow/deny 都可稳定序列化；
    5. telemetry 不泄漏敏感输入（详情日志需显式开关）。

    推荐新增工具自测最小清单：

    • unknown tool 名称
    • schema 错误输入
    • validateInput 拒绝
    • permission deny
    • call throw
    • call success + post hook
    • user interrupt during execution
