AgentLoop 与 Tool：Streaming、StopHooks 与输出边界（深潜审计版）

1) Scope 与 Evidence Boundary

本页覆盖两条关键链：

  1. src/services/tools/StreamingToolExecutor.ts 的流式工具调度；
  2. src/query/stopHooks.ts 的回合末治理与阻断。

以及它们在 src/query.ts 中的衔接点（fallback/abort/drain）。

不覆盖： - 单工具权限判定实现细节（见 04）； - query 主循环全量状态机（见 02）； - transport/UI 展示层实现（见 07）。

2) Core Thesis

Streaming 路径最大的工程难点是三件事同时成立：

  • 进度要实时可见；
  • 结果拓扑要完整（tool_use 对偶 tool_result）；
  • fallback/abort 时不能泄漏旧流孤儿结果。

StreamingToolExecutor + query.ts + stopHooks.ts 的组合就是为了解这个三难。

3) Runtime State Ownership

3.1 StreamingToolExecutor 内部状态

type ToolStatus = 'queued' | 'executing' | 'completed' | 'yielded'

private tools: TrackedTool[] = []
private toolUseContext: ToolUseContext
private hasErrored = false
private erroredToolDescription = ''
private siblingAbortController: AbortController
private discarded = false
private progressAvailableResolve?: () => void

关键含义： - tools 是执行队列与结果缓存； - siblingAbortController 用于“兄弟工具级联取消”； - discarded 标记 fallback 后整个旧流作废； - progressAvailableResolve 用于 progress 的异步唤醒。

3.2 stopHooks.ts 返回结构

type StopHookResult = {
  blockingErrors: Message[]
  preventContinuation: boolean
}

stop hooks 不是“仅输出日志”，而是具有 continuation 裁决权。

4) End-to-end Flow

4.1 从 query 到 streaming executor

query.ts 流式收到 tool_use 后：

if (streamingToolExecutor && !toolUseContext.abortController.signal.aborted) {
  for (const toolBlock of msgToolUseBlocks) {
    streamingToolExecutor.addTool(toolBlock, message)
  }
}

并在流中不断消费已完成结果：

for (const result of streamingToolExecutor.getCompletedResults()) {
  if (result.message) {
    yield result.message
    toolResults.push(...normalizeMessagesForAPI([result.message], ...).filter(_ => _.type === 'user'))
  }
}

4.2 回合末必须 drain remaining

const toolUpdates = streamingToolExecutor
  ? streamingToolExecutor.getRemainingResults()
  : runTools(...)

这是协议完整性的关键：即使中断，也要让 executor 产出 synthetic tool_result。

4.3 无 follow-up 后进入 stop hooks

const stopHookResult = yield* handleStopHooks(...)
if (stopHookResult.preventContinuation) {
  return { reason: 'stop_hook_prevented' }
}
if (stopHookResult.blockingErrors.length > 0) {
  ...
  continue
}

5) Guard / Decision Matrix

Guard 条件 动作 输出
canExecuteTool 无执行中工具，或全为安全并发且当前也安全 启动执行 status=executing
非安全工具阻断 执行中有工具且当前不安全 break 队列推进 保序
sibling_error Bash 返回 error tool_result siblingAbortController.abort('sibling_error') 兄弟工具合成取消结果
user interrupt abort reason=interrupt 且工具可 cancel synthetic user_interrupted error tool_result
streaming fallback query 通知 fallback discard() + 新 executor 旧流结果作废
stop hook prevent hook 返回 preventContinuation 返回终止 stop_hook_prevented
stop hook blocking blockingErrors > 0 回灌错误继续 stop_hook_blocking

6) Failure / Recovery / Degradation

6.1 synthetic error 统一构造

private createSyntheticErrorMessage(
  toolUseId: string,
  reason: 'sibling_error' | 'user_interrupted' | 'streaming_fallback',
  assistantMessage: AssistantMessage,
): Message {
  if (reason === 'user_interrupted') {
    return createUserMessage({ ... withMemoryCorrectionHint(REJECT_MESSAGE) ... })
  }
  if (reason === 'streaming_fallback') {
    return createUserMessage({ ... 'Streaming fallback - tool execution discarded' ... })
  }
  const msg = desc
    ? `Cancelled: parallel tool call ${desc} errored`
    : 'Cancelled: parallel tool call errored'
  return createUserMessage({ ... msg ... })
}

这段把取消原因结构化，避免“都叫失败”造成误判。

6.2 fallback 时作废旧执行器

query.ts 在 fallback 中会： - tombstone 旧 assistant； - 清空 assistantMessages/toolResults/toolUseBlocks； - streamingToolExecutor.discard() 并重建。

语义：旧流结果全部作废，防止 tool_use_id 对不上。

6.3 Bash 错误级联取消

if (isErrorResult) {
  thisToolErrored = true
  if (tool.block.name === BASH_TOOL_NAME) {
    this.hasErrored = true
    this.erroredToolDescription = this.getToolDescription(tool)
    this.siblingAbortController.abort('sibling_error')
  }
}

语义：只对 Bash 做级联取消，因为 Bash 常含隐式依赖链。

6.4 stop hooks 异常降级

handleStopHooks 捕获异常后： - 记录 tengu_stop_hook_error； - yield createSystemMessage(..., 'warning')； - 返回 preventContinuation: false。

语义：治理路径失败不应击穿主链。

7) Invariants

  1. fallback/abort 后不能遗留无结果 tool_use。
  2. getRemainingResults() 必须在结束前被消费。
  3. non-concurrency-safe 工具前序约束不可被并发工具穿透。
  4. progress 可抢先输出，但最终结果顺序必须可解释。
  5. stop hook 的阻断必须通过 preventContinuation/blockingErrors/attachment 显式表达。
  6. 主线程专属 cleanup 不得被子 agent 越权触发。
  7. discarded=true 时 executor 不应继续产出旧流业务结果。

8) Cross-module Contracts

  • 与 query.ts：executor 只负责执行与消息产出，终止策略归 query。
  • 与 toolExecution.ts：单工具错误语义由 toolExecution 统一消息化，executor 不二次改写业务错误。
  • 与 stopHooks.ts：stop hooks 消费完整 turn 快照并返回结构化裁决，不直接写 query state。

9) Engineering Constraints / Evolution Guidance

新增 abort/fallback reason 时必须同步：

  1. 扩展 synthetic error 原因枚举；
  2. 定义是否上冒泡到父级 abortController；
  3. 验证 getCompletedResults/getRemainingResults 的输出一致性；
  4. 验证 query 收尾阶段是否仍能补齐 tool_result。

建议回归场景：

  • streaming 中途 fallback；
  • 两个并发 Bash，其中一个失败；
  • user interrupt + cancel/block 混合工具；
  • stop hook 返回 blockingErrors 与 preventContinuation。
