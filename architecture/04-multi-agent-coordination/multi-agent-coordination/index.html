    多 Agent 协同：执行后端、权限控制与隔离收尾（深潜审计版）

    1) Scope 与 Evidence Boundary

    本页覆盖 04 模块“全链协同状态机”：从 spawn 入口到 backend 选择、permission mailbox、team/task 状态一致性、worktree 生命周期与 bridge 收尾。

    证据范围：

    • src/tools/shared/spawnMultiAgent.ts
    • src/utils/swarm/backends/registry.ts
    • src/utils/swarm/backends/detection.ts
    • src/utils/swarm/inProcessRunner.ts
    • src/utils/swarm/permissionSync.ts
    • src/utils/swarm/teamHelpers.ts
    • src/utils/tasks.ts
    • src/utils/worktree.ts
    • src/bridge/bridgeMain.ts
    • src/bridge/bridgePointer.ts

    不覆盖：

    • 单 agent query/tool 执行语义（见 01 模块）；
    • memory/compact 内部算法（见 02/03 模块）；
    • slash 命令入口定义本体（仅引用其协同后果）。

    2) Core Thesis

    04 模块的核心不是“并行执行”，而是把多执行单元压成可审计、可恢复、可回收的一致协议：

    1. spawn 输入被归一为稳定身份与模型语义；
    2. backend 选择遵守 explicit/auto 分支契约；
    3. 权限请求必须经过 leader 事实源；
    4. team/task 状态可在异常后重建；
    5. worktree 与 bridge 退出按安全顺序收敛。

    3) Runtime State Ownership

    状态类别 所有者 关键函数/字段 说明
    spawn 决策态 spawnMultiAgent.ts spawnTeammate / handleSpawn / resolveTeammateModel 输入校验、分支分流、模型继承
    backend 探测/退化态 registry.ts + detection.ts detectAndGetBackend / isInProcessEnabled / markInProcessFallback 执行后端稳定选择
    in-process 运行态 inProcessRunner.ts runInProcessTeammate 长生命周期 worker 执行循环
    权限协商态 permissionSync.ts mailbox request/response + pollForResponse leader-worker 审批闭环
    团队持久态 teamHelpers.ts + tasks.ts 成员/mode/active + task list owner 会话态与持久态一致
    worktree 生命周期态 worktree.ts session/agent worktree create/keep/cleanup 隔离目录创建与安全删除
    bridge 收尾态 bridgeMain.ts + bridgePointer.ts onSessionDone / onSessionTimeout / pointer clear 超时/结束后的系统收敛

    4) End-to-end Flow

    4.1 Spawn -> Backend -> Execute

    1. spawnTeammate 接收请求，resolveTeammateModel 归一 inherit 语义；
    2. handleSpawn 根据模式与探测结果选择 in-process / pane backend；
    3. 成功后将 teammate 注册到 team/task 状态载体。

    4.2 Permission 协商与状态回写

    1. worker 触发工具权限请求，构造 SwarmPermissionRequest；
    2. sendPermissionRequestViaMailbox 发往 leader mailbox；
    3. leader 决策后 sendPermissionResponseViaMailbox 回写；
    4. worker pollForResponse 收敛到继续/拒绝分支；
    5. syncTeammateMode、setMemberActive 等持续维护 team 可观测状态。

    4.3 Worktree 与 Bridge 收尾

    1. 需要隔离时 createWorktreeForSession 或 createAgentWorktree 创建目录；
    2. 退出时按 keep/cleanup 分支处理；
    3. bridge 在 onSessionDone/onSessionTimeout 执行终止与清理；
    4. clearBridgePointer 收尾，避免脏指针误导后续恢复。

    5) Guard / Decision Matrix

    Guard 条件 动作 结果
    model inherit guard inputModel='inherit' 继承 leader model 或默认 teammate model 防把 inherit 当字面模型
    explicit backend guard mode 非 auto 且探测失败 直接错误返回 防静默执行语义漂移
    auto fallback guard auto 且后端不可用 markInProcessFallback 后走 in-process 可用性优先
    permission routing guard team/leader/worker 缺失 拒绝发消息并返回失败 防无目标权限请求
    permission response guard response subtype 不合法或 ID 不匹配 视为无效并继续等待/失败 防错误响应污染
    team write guard mode/active 无变化 不写盘 降低竞争写与抖动
    stale cleanup guard dirty 或 unpushed 跳过删除 防误删用户工作
    shutdown idempotency guard 已 shutdownRequested 短路重复终止 防双重 cleanup

    6) Failure / Recovery / Degradation

    6.1 Backend 失败恢复

    • explicit 模式失败：直接 surface（可行动错误）；
    • auto 模式失败：退化 in-process（fail-open 可用路径）。

    6.2 Permission 信道恢复

    • mailbox 发送失败：返回 false，调用侧可重试或回退；
    • response 轮询超时/异常：收敛为失败结果，不阻塞主会话无限等待。

    6.3 Team/Task 状态恢复

    • 单文件读取/解析失败：局部跳过，避免全局崩溃；
    • cleanupSessionTeams 使用 Promise.allSettled，防止“一处失败阻断全部收尾”。

    6.4 Worktree 清理恢复

    • git/hook 删除失败：保留现场并上报，不激进强删；
    • stale 清理遇到任一步失败：跳过该 worktree，保持 fail-closed。

    6.5 Bridge 终止恢复

    • 正常 done 与 timeout 都走终止收敛分支；
    • pointer 清理失败不应导致再次启动时误判活跃会话，需显式记录并重试入口可见。

    7) Invariants

    1. worker 权限最终态必须由 leader 决策路径给出。
    2. explicit backend 模式不得被 silent fallback 覆盖。
    3. agent_id、team_name、mailbox sender/recipient 必须可映射。
    4. inherit 必须在入口层归一，不得透传到底层执行器。
    5. team 会话态与持久态更新必须同轮收敛。
    6. worktree 删除前必须满足安全检查（无改动/无未推送）。
    7. 退出流程必须保持幂等，重复终止不应触发二次破坏。
    8. auto 清理策略必须默认 fail-closed，而非“删错比漏删好”。

    8) Cross-module Contracts

    • 对 01（agentloop/tool）：04 只负责多单元编排，不改消息执行语义。
    • 对 06（hooks/permissions）：04 的 permission mailbox 需服从统一权限策略源。
    • 对 02/03（memory/compact）：worker 运行可触发 compact，但 compact 成果不应反向破坏协同状态。
    • 对 CLI/UI 层：展示信息以 team/task 持久态为准，mailbox 仅作瞬时通道。
    • 对 worktree 命令层：共享同一生命周期安全约束，禁止并行定义“第二套删除规则”。

    9) Engineering Constraints / Evolution Guidance

    新增后端或协同能力时必须验证：

    1. 是否完整接入 explicit/auto 的 guard 分支；
    2. 是否接入统一 permission mailbox 协议；
    3. 是否维护 team/task 双载体一致性；
    4. 是否遵守 worktree fail-closed 删除策略；
    5. 是否在 timeout/abort 路径保持幂等收尾。

    建议回归：

    • explicit tmux 失败 vs auto fallback；
    • mailbox 请求成功/失败/超时；
    • team mode/active 同步与 cleanup；
    • dirty/unpushed worktree 下 stale cleanup 跳过；
    • bridge done/timeout 两路径终止与指针清理。
