    多 Agent 协同（入口审计页）

    1) Scope 与 Evidence Boundary

    本页是 docs/architecture/04-multi-agent-coordination 的入口页，只负责模块边界、阅读顺序与页面所有权，不承载子机制深潜。

    证据边界覆盖：

    • src/tools/shared/spawnMultiAgent.ts
    • src/utils/swarm/backends/*.ts
    • src/utils/swarm/permissionSync.ts
    • src/utils/swarm/teamHelpers.ts
    • src/utils/tasks.ts
    • src/utils/worktree.ts
    • src/bridge/bridgeMain.ts

    2) Core Thesis

    04 模块是“多执行单元协同治理层”：在不同后端与隔离策略下，保持 teammate 的创建、权限、状态与清理语义一致且可恢复。

    它解决的不是“多开几个 agent”，而是“多 agent 失败后仍能正确收敛”。

    3) Runtime State Ownership

    状态 所有者 说明
    spawn/继承语义 spawnMultiAgent.ts 输入归一、模型继承、执行分流
    backend 决策态 backends/registry.ts + detection.ts auto/explicit 选择与 fallback
    权限协商态 permissionSync.ts + mailbox leader-worker 请求/响应闭环
    团队持久态 teamHelpers.ts + tasks.ts 成员、mode、active 与任务归属
    隔离与回收态 worktree.ts + bridgeMain.ts 会话/agent worktree 生命周期与退出收尾

    4) End-to-end Flow（高层）

    1. spawn 入口接收 teammate 请求并归一参数。
    2. backend 层按模式与环境选择执行后端。
    3. worker 执行中通过 mailbox 与 leader 做权限同步。
    4. team/task 状态持续回写，保证 UI 与恢复链一致。
    5. 会话结束或超时后执行 worktree/teammate 清理与指针收尾。

    5) Guard / Decision Matrix（入口级）

    Guard 条件 行为 结果
    显式后端保护 mode != auto 且探测失败 直接报错 防静默语义漂移
    auto fallback mode=auto 且后端不可用 回落 in-process 可用性优先
    权限请求必备标识 缺 team/leader/worker 拒绝发送请求 防无目标消息
    worktree 删除前检查 dirty/unpushed 拒绝自动删 防误删变更
    退出路径幂等 已 shutdownRequested 跳过重复终止 防双重清理

    6) Failure / Recovery / Degradation

    • backend 检测失败：auto 退化到 in-process；explicit 模式直接可行动错误。
    • mailbox 异常：请求失败可重试/回退，不应拖垮主循环。
    • team 文件异常：局部失败返回防御值，避免整队列崩溃。
    • worktree 清理异常：优先保留现场并上报，而非激进删除。

    7) Invariants

    1. worker 不得绕过 leader 自主完成最终权限决策。
    2. 显式执行模式不得被静默 fallback 覆盖。
    3. team identity 在会话态与持久态必须可映射。
    4. worktree 自动清理不得删除有未提交/未推送变更的目录。
    5. 清理顺序必须“先停执行，再清状态，再删目录”。
    6. 模型继承别名（如 inherit）必须在入口层归一。

    8) Cross-module Contracts

    • 对 01（agentloop/tool）：04 提供协同编排，不改 query/tool 消息语义。
    • 对 06（stop hooks/permission）：权限决策仍以 leader 规则层为事实源。
    • 对 worktree 命令链：04 复用统一 worktree 生命周期约束，不定义第二套删除语义。
    • 对 UI：状态展示基于 team/task 持久态，不依赖瞬时 mailbox 假设。

    9) Engineering Constraints / Evolution Guidance

    扩展 04 模块时必须：

    1. 先补协议分支（成功/退化/失败），再加后端能力；
    2. 新后端必须接入统一 permission/mailbox 契约；
    3. 新清理逻辑必须证明不破坏“先停后删”顺序；
    4. 入口页与主文职责分离：README 只做导航，深潜放子页与主文。
