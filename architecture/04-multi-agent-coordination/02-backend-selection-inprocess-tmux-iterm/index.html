多 Agent 协同：Backend 选择（in-process / tmux / iTerm）（深潜审计版）

1) Scope 与 Evidence Boundary

本页覆盖“如何选择执行后端”与“不可用时如何退化”，证据范围：

  • src/utils/swarm/backends/registry.ts
  • src/utils/swarm/backends/detection.ts
  • src/utils/swarm/inProcessRunner.ts
  • src/utils/swarm/teammateContext.ts

不覆盖：

  • spawn 参数与模型继承（见 01）；
  • permission/mailbox 协议（见 03）；
  • worktree 清理流程（见 04）。

2) Core Thesis

backend 层的核心目标不是“选最快后端”，而是让 auto 与 explicit 语义在所有环境下都可解释：

  1. explicit 失败应立刻可见；
  2. auto 失败应受控退化；
  3. 单会话后端结果应稳定（缓存/标记）；
  4. in-process worker 在长生命周期下保持可观察与可恢复。

3) Runtime State Ownership

状态类别 所有者 关键函数/字段 说明
探测缓存态 registry.ts cachedDetectionResult / cachedBackend 单进程后端稳定器
fallback 态 registry.ts inProcessFallbackActive / markInProcessFallback auto 失败后强制 in-process
执行模式判定态 registry.ts isInProcessEnabled mode + 终端环境综合判断
环境探测态 detection.ts isInsideTmux / isInITerm2 / isIt2CliAvailable / isTmuxAvailable 可用性事实源
in-process 运行态 inProcessRunner.ts runInProcessTeammate worker 主循环与任务状态
teammate 上下文态 teammateContext.ts runWithTeammateContext 隔离上下文运行边界

4) End-to-end Flow

  1. detectAndGetBackend 确保后端注册并执行探测；
  2. 按优先级判断：tmux 内 -> iTerm native -> iTerm+tmux fallback -> tmux external -> error；
  3. isInProcessEnabled 融合用户模式与 fallback 标记给最终执行选择；
  4. 若走 in-process，runInProcessTeammate 启动长生命周期循环；
  5. 状态与异常通过任务/事件路径回传给上层。
// src/utils/swarm/backends/registry.ts
export async function detectAndGetBackend(): Promise<BackendDetectionResult> {
  await ensureBackendsRegistered()
  if (cachedDetectionResult) return cachedDetectionResult

  if (await isInsideTmux()) {
    return { backend: createTmuxBackend(), isNative: true, needsIt2Setup: false }
  }

  if (isInITerm2()) {
    if (await isIt2CliAvailable()) {
      return { backend: createITermBackend(), isNative: true, needsIt2Setup: false }
    }
    if (await isTmuxAvailable()) {
      return { backend: createTmuxBackend(), isNative: false, needsIt2Setup: true }
    }
  }
  ...
}

5) Guard / Decision Matrix

Guard 条件 动作 结果
detection cache guard 已有 cachedDetectionResult 复用缓存 防会话抖动
explicit mode guard mode 非 auto 且探测失败 直接失败 保持用户意图
auto fallback guard auto + 探测失败 markInProcessFallback 可用性退化
non-interactive guard 非交互环境 强制 in-process 防 pane 路径不可达
inside tmux guard isInsideTmux=true 优先 tmux native 保持环境一致
iTerm setup guard iTerm 且 it2 缺失 提示 setup 或 tmux fallback 可行动诊断
backend reset guard 显式 reset 清空缓存 支持重探测验证

6) Failure / Recovery / Degradation

6.1 探测失败

  • explicit：报错并结束；
  • auto：回退 in-process。

6.2 iTerm 不完整安装

  • it2 CLI 缺失但 tmux 存在：降级 tmux 并提示 setup；
  • 两者都不可用：返回安装指引错误。

6.3 in-process runner 异常

  • worker 内异常收敛为任务失败/事件回传；
  • 不应升级为主进程级崩溃。

6.4 状态退化

  • fallback 激活后保持稳定执行路径，避免重复探测风暴。

7) Invariants

  1. explicit 模式失败必须可见，不得 silent fallback。
  2. auto 模式 fallback 必须可观测且可追踪。
  3. 会话内后端判定一旦缓存，不应随机漂移。
  4. in-process runner 必须可中断、可上报状态。
  5. 后端探测层与策略层职责分离（能不能 vs 该不该）。
  6. teammate 上下文必须通过专用 context 运行边界注入。

8) Cross-module Contracts

  • 对 01（spawn）：02 只消费 mode/intent，不重写模型继承语义。
  • 对 03（permission）：02 选择后端后仍必须使用统一权限协议。
  • 对 04（worktree）：02 不决定隔离目录生命周期，仅决定执行载体。
  • 对 bridge 层：02 输出的后端行为必须可被收尾路径统一处理。

9) Engineering Constraints / Evolution Guidance

新增后端时必须验证：

  1. 是否接入 detectAndGetBackend 决策链；
  2. 是否遵守 explicit/auto 分支语义；
  3. 是否具备失败后可行动诊断；
  4. 是否与 in-process fallback 状态互斥/兼容清晰。

建议回归：

  • inside tmux / iTerm / headless / plain shell 组合；
  • explicit tmux 失败 vs auto fallback；
  • reset 后重探测一致性；
  • in-process 异常回传与继续运行能力。
