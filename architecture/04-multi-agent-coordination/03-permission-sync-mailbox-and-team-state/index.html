多 Agent 协同：权限同步、Mailbox 与团队状态（深潜审计版）

1) Scope 与 Evidence Boundary

本页覆盖“leader-worker 权限协商”与“team/task 持久态一致性”，证据范围：

  • src/utils/swarm/permissionSync.ts
  • src/utils/swarm/teamHelpers.ts
  • src/utils/tasks.ts
  • mailbox 写入路径（permissionSync 调用侧）

不覆盖：

  • spawn 入口与 backend 选择（见 01/02）；
  • worktree 创建/清理（见 04）。

2) Core Thesis

03 页的核心是把“权限确认”从单点交互升级为可恢复协议：

  1. 请求/响应必须具备 requestId 关联；
  2. worker 不得绕过 leader 直接形成批准终态；
  3. mailbox 为瞬时通道，team/task 为恢复事实源；
  4. 失败要可重试、可超时、可局部降级。

3) Runtime State Ownership

状态类别 所有者 关键函数 说明
请求构造态 permissionSync.ts createPermissionRequest requestId/tool/use 元数据封装
文件兼容态 permissionSync.ts writePermissionRequest / readPendingPermissions / resolvePermission pending/resolved 文件路径兼容
mailbox 协议态 permissionSync.ts sendPermissionRequestViaMailbox / sendPermissionResponseViaMailbox leader-worker 异步协商
轮询收敛态 permissionSync.ts pollForResponse / deleteResolvedPermission worker 等待与收尾删除
团队成员态 teamHelpers.ts setMemberMode / setMemberActive / syncTeammateMode mode/active 同步
会话清理态 teamHelpers.ts cleanupSessionTeams 结束时团队目录/进程回收
任务归属态 tasks.ts setLeaderTeamName / getTaskListId / unassignTeammateTasks 任务所有者与回收

4) End-to-end Flow

  1. worker 构造 SwarmPermissionRequest；
  2. sendPermissionRequestViaMailbox 发送到 leader；
  3. leader 通过 sendPermissionResponseViaMailbox 回写结果；
  4. worker pollForResponse 等待并应用批准/拒绝；
  5. mode/active 与任务归属持续写入 team/task 持久态；
  6. 会话结束时 cleanupSessionTeams + 任务回收，移除残留协作状态。
// src/utils/swarm/permissionSync.ts
export async function sendPermissionRequestViaMailbox(
  request: SwarmPermissionRequest,
): Promise<boolean> {
  const leaderName = await getLeaderName(request.teamName)
  if (!leaderName) {
    return false
  }
  ...
  await writeToMailbox(leaderName, {...}, request.teamName)
  return true
}

5) Guard / Decision Matrix

Guard 条件 动作 结果
leader target guard leaderName 缺失 发送失败返回 false 防无目标广播
request identity guard 缺 requestId/toolUseId 拒绝构造/发送 防不可追踪审批
response match guard requestId 不匹配 忽略并继续轮询 防串单污染
mailbox write guard 写入异常 返回失败 + 上层可重试 防阻塞主循环
mode sync guard mode 未变化 不写盘 降低竞争写
active sync guard member 不存在 跳过更新 防脏写
cleanup guard 单 team 清理失败 allSettled 聚合继续 防全局收尾中断

6) Failure / Recovery / Degradation

6.1 mailbox 发送失败

  • 返回 false；
  • 调用方可重试或降级为错误 surface。

6.2 response 超时/缺失

  • pollForResponse 超时返回失败结果；
  • worker 不应无限等待。

6.3 文件态损坏

  • pending/resolved 解析异常局部跳过；
  • 不因单坏文件拖垮整个审批流。

6.4 团队清理异常

  • cleanupSessionTeams 使用 Promise.allSettled；
  • 失败项记录，成功项先完成，防雪崩阻断。

7) Invariants

  1. 权限最终批准必须来自 leader 决策通路。
  2. request 与 response 必须通过 requestId 绑定。
  3. mailbox sender/recipient 必须与 team member 身份可映射。
  4. mode/active 写盘是事实回写，不应由 UI 推断替代。
  5. 会话收尾必须执行团队与任务双通道清理。
  6. 任何单点失败都不应使审批系统进入永久阻塞态。

8) Cross-module Contracts

  • 对 01/02：不管如何 spawn 或选 backend，权限链路都走统一 mailbox 协议。
  • 对 04：权限流程使用的成员状态需可被 worktree/会话清理正确回收。
  • 对 task 系统：团队身份变化需同步到任务归属，避免“孤儿任务”。
  • 对 UI：展示应读 team/task 持久态，不以瞬时消息包为最终状态。

9) Engineering Constraints / Evolution Guidance

新增权限字段或通道时必须验证：

  1. request/response 关联是否仍唯一；
  2. mailbox 与文件兼容路径是否语义一致；
  3. 是否引入 leader 旁路审批；
  4. 是否保留超时与清理收敛路径。

建议回归：

  • leader 缺失场景；
  • requestId 不匹配场景；
  • mailbox 写失败与重试；
  • cleanup 过程中部分失败场景；
  • 任务反注册与状态清理联动。
