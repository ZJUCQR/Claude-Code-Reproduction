MCP 协议：CLI/UI 管理与插件集成（深潜审计版）

1) Scope 与 Evidence Boundary

本页覆盖“MCP 管理面”：CLI handlers、print 管理流程、pending approvals、插件/配置集成与运行时刷新。

证据范围：

  • src/cli/handlers/mcp.tsx
  • src/cli/print.ts
  • src/services/mcpServerApproval.tsx
  • src/services/mcp/mcpStringUtils.ts（管理面显示/命名关联）

不覆盖：

  • transport/auth 建连机制（见 01）；
  • discovery 实体投影（见 02）；
  • 调用与结果后处理（见 03）。

2) Core Thesis

管理面的目标不是“提供命令菜单”，而是让配置变更、审批决策与运行时状态形成闭环：

  1. add/remove/reset/reconnect 等操作必须回流 runtime；
  2. pending server 必须先审批后可用；
  3. SDK client 变化需要自动刷新；
  4. CLI 与 UI 必须共享同一配置事实源。

3) Runtime State Ownership

状态类别 所有者 关键函数 说明
CLI 命令态 handlers/mcp.tsx mcpListHandler / mcpGetHandler / mcpAddJsonHandler / mcpRemoveHandler / mcpResetChoicesHandler 增删改查与重置入口
管理刷新态 print.ts handleMcpSetServers / reconcileMcpServers / updateSdkMcp 配置变化与 SDK 集合同步
审批决策态 mcpServerApproval.tsx handleMcpjsonServerApprovals pending server 人工审批
命名展示态 mcpStringUtils.ts getMcpDisplayName / extractMcpToolDisplayName CLI/UI 统一展示名称

4) End-to-end Flow

  1. 用户通过 CLI/UI 触发 MCP 配置操作；
  2. handlers 执行 add/list/get/remove/reset 等命令；
  3. handleMcpSetServers / reconcileMcpServers 比较并应用 server 集合变化；
  4. updateSdkMcp 根据 new/removed/failed/pending 状态刷新 SDK clients；
  5. handleMcpjsonServerApprovals 处理 project pending servers（单个/多个审批）；
  6. 变更后 runtime 连接与发现路径按新配置继续运行。

5) Guard / Decision Matrix

Guard 条件 动作 结果
pending approval guard 存在 pending project servers 触发审批流程 防未授权启用
single/multi approval guard pending 数量=1/多 单项确认 / 多选确认 减少误操作
set-servers reconcile guard 新旧集合差异 add/remove/refresh 配置与 runtime 一致
sdk refresh guard new/removed/failed/pending 变化 updateSdkMcp 重建集合 防 SDK 漂移
remove scope guard 跨 scope 名称冲突 要求显式范围 防误删
display-name guard user-facing 显示需求 统一 displayName 规则 防命名混乱

6) Failure / Recovery / Degradation

6.1 命令执行失败

  • handler 返回可行动错误；
  • 不破坏已有可用 server 集合。

6.2 审批流程失败

  • 审批流程失败仅影响 pending server；
  • 已启用 server 继续可用。

6.3 SDK client 漂移

  • 检测到 failed/pending/new/removed 后 updateSdkMcp 触发重建；
  • 防长期持有失效对象。

6.4 reconcile 失败

  • 集合调和失败时保留现有状态并记录错误；
  • 避免部分写入后运行时不一致。

7) Invariants

  1. pending project servers 未审批前不得进入可用集。
  2. CLI 与 UI 必须共享同一配置事实源。
  3. set/remove/reconnect 操作后 runtime 视图必须可收敛。
  4. SDK clients 变化必须可检测并可刷新。
  5. 名称展示规则必须稳定，避免误操作目标。
  6. 管理面异常不得中断核心调用链。

8) Cross-module Contracts

  • 对 01：04 管理变更会触发连接重建/刷新，但不重写 transport 语义。
  • 对 02：server 管理结果直接影响发现集合可见性。
  • 对 03：审批与管理决定哪些 server 可进入调用/协商路径。
  • 对主链：管理面应提供可解释状态，不输出协议细节噪声。

9) Engineering Constraints / Evolution Guidance

新增管理命令或审批流程时必须验证：

  1. 是否接入 reconcile 与 runtime 刷新闭环；
  2. 是否保持 pending 审批门禁；
  3. 是否在多 scope 命名下避免误删/误改；
  4. 是否在失败场景保持已启用能力稳定。

建议回归：

  • list/get/add/remove/reset 全命令链；
  • pending 单个与多个审批；
  • SDK refresh（new/removed/failed/pending）；
  • set-servers 后 runtime 变化可见性。
