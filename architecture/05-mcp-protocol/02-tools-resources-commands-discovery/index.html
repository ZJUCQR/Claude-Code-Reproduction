MCP 协议：Tools / Resources / Commands 发现（深潜审计版）

1) Scope 与 Evidence Boundary

本页覆盖“连接成功后能力发现与内部对象投影”，证据范围：

  • src/services/mcp/client.ts
  • src/services/mcp/mcpStringUtils.ts

不覆盖：

  • 连接/鉴权与重连（见 01）；
  • 调用后结果转换与 elicitation 重试（见 03）；
  • CLI/UI 配置管理入口（见 04）。

2) Core Thesis

发现层的核心不是“多拉几个 list 接口”，而是保证 capability 差异与 server 局部失败不会污染全局工具视图：

  1. capability 缺失时应稳定降级为空集合；
  2. tools/resources/commands 三路发现语义一致；
  3. tool 命名、权限映射与显示名规则可预测；
  4. 单 server 失败不阻断全量聚合。

3) Runtime State Ownership

状态类别 所有者 关键函数 说明
tools 发现态 client.ts fetchToolsForClient tools/list 拉取与 Tool 包装
resources 发现态 client.ts fetchResourcesForClient resources/list 拉取与投影
commands 发现态 client.ts fetchCommandsForClient prompts/list 到 Command 包装
聚合态 client.ts getMcpToolsCommandsAndResources 多 server 合并与局部容错
名称映射态 mcpStringUtils.ts buildMcpToolName / getMcpPrefix / getMcpDisplayName 命名空间与展示名稳定化
权限输入态 client.ts + mcpStringUtils.ts mcpToolInputToAutoClassifierInput / getToolNameForPermissionCheck classifier/权限检查输入

4) End-to-end Flow

  1. 聚合器获取连接后，分别调用 tools/resources/commands 发现路径；
  2. fetchToolsForClient 对工具描述、权限 hint、调用包装做投影；
  3. fetchResourcesForClient 投影资源对象并绑定 server 标识；
  4. fetchCommandsForClient 将 prompts 映射为命令入口；
  5. getMcpToolsCommandsAndResources 合并结果并在 server 级别隔离失败。
// src/services/mcp/client.ts
export const fetchToolsForClient = memoizeWithLRU(async (client) => {
  if (client.type !== 'connected') return []
  if (!client.capabilities?.tools) return []
  const result = await client.client.request({ method: 'tools/list' }, ListToolsResultSchema)
  return result.tools.map(tool => ({ ...MCPTool, name: buildMcpToolName(client.name, tool.name), isMcp: true }))
}, (client) => client.name, MCP_FETCH_CACHE_SIZE)

5) Guard / Decision Matrix

Guard 条件 动作 结果
connected guard client.type !== connected 返回 [] 降低故障扇出
capability guard 无 tools/resources/prompts capability 返回 [] 防无意义请求
request failure guard list 请求异常 记录并返回 [] server 级降级
namespace guard server/tool 名组合 通过 mcp__... 构造 防跨 server 冲突
permission-name guard tool 元信息存在 mcpInfo getToolNameForPermissionCheck 归一 权限检查稳定
aggregator isolation guard 单 server process 异常 捕获后继续其它 server partial availability

6) Failure / Recovery / Degradation

6.1 list 请求失败

  • tools/resources/commands 各自降级为 []；
  • 全局聚合继续。

6.2 capability 缺失

  • 明确按 capability gate 跳过，而不是抛错；
  • 避免不支持能力的 server 拖慢路径。

6.3 命名冲突风险

  • 通过 server 前缀命名空间隔离；
  • 可选策略（如 skipPrefix）需受控，不得默认破坏隔离。

6.4 聚合期异常

  • 单 server 异常局部化；
  • 结果仍输出可用子集。

7) Invariants

  1. 非 connected client 的发现结果必须为空。
  2. 三类发现路径必须统一“失败降级为空”的语义。
  3. tool 名称必须可映射回 server+tool 原始标识。
  4. 权限检查工具名必须使用统一归一规则。
  5. 聚合器不得因单 server 异常短路全局。
  6. discovery 结果必须可直接供主链注册使用。

8) Cross-module Contracts

  • 对 01：02 消费连接守卫，不重复定义连接恢复语义。
  • 对 03：02 产出的 tool/command/resource 是调用与结果处理的输入边界。
  • 对 04：CLI/UI 的 server 配置变化应反映到 02 的发现集合。
  • 对权限系统：02 仅提供 hint 与名称映射，不替代策略层审批。

9) Engineering Constraints / Evolution Guidance

新增发现对象或映射逻辑时必须验证：

  1. 是否遵守 connected + capability 双 gate；
  2. 是否保持 server 级失败隔离；
  3. 是否破坏命名空间稳定性；
  4. 是否影响权限检查输入兼容性。

建议回归：

  • connected/断连 server 混合；
  • capability 缺失组合；
  • list 请求局部失败；
  • 命名映射与权限输入的一致性。
