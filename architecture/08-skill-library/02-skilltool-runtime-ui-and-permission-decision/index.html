SkillTool 运行时、UI 与权限决策（深潜审计版）

1) Scope 与 Evidence Boundary

本页只覆盖 08 模块里“模型平面如何通过 SkillTool 调用 skill”的运行时层：

  • skill 输入校验
  • deny/allow/ask 权限顺序
  • inline/fork/remote canonical 执行分叉
  • tool_result 统一回传语义
  • 与 command registry 的关系

证据范围：

  • src/tools/SkillTool/SkillTool.ts
  • src/commands.ts
  • src/utils/forkedAgent.ts
  • src/utils/argumentSubstitution.ts（用于参数语义锚点）

不覆盖：

  • discovery/frontmatter/loading（见 01）
  • slash 用户入口与后台 fork 回注（见 03）
  • bundled/plugin/MCP taxonomy（见 04）

2) Core Thesis

SkillTool 不是“模型版 slash 包装器”，而是同一命令事实源上的授权执行壳。它做四件事：

  1. 把可调用目标限定为 prompt skill；
  2. 把权限判决序列固定为 deny-first；
  3. 把 inline/fork/remote canonical 三条执行通路统一回 tool_result 协议；
  4. 把来源差异（本地/MCP/remote）在正确层面恢复，而不是混成一条“统一安全假设”。

3) Runtime State Ownership

状态类别 所有者 关键函数 职责
运行期命令汇总态 SkillTool.ts getAllCommands 本地 commands + MCP skill commands 合流
输入校验态 SkillTool.ts validateInput 阻断空输入、未知 skill、非 prompt、禁模型调用
权限裁决态 SkillTool.ts checkPermissions deny > (canonical allow) > allow > safe-auto-allow > ask
执行分叉态 SkillTool.ts call, executeForkedSkill, executeRemoteSkill inline/fork/remote 路由
上下文补丁态 SkillTool.ts contextModifier allowedTools/model/effort 注入后续上下文
结果协议态 SkillTool.ts mapToolResultToToolResultBlockParam fork/inline 结果统一 tool_result 输出
命令投影视图态 commands.ts getSkillToolCommands, getMcpSkillCommands, getSlashCommandToolSkills 不同 consumer 的可见命令面分层

4) End-to-end Flow

4.1 命令汇总先做 MCP 精确过滤

getAllCommands() 不把所有 MCP prompt 放进来，只纳入 loadedFrom === 'mcp' 的 skill：

const mcpSkills = context
  .getAppState()
  .mcp.commands.filter(
    cmd => cmd.type === 'prompt' && cmd.loadedFrom === 'mcp',
  )
if (mcpSkills.length === 0) return getCommands(getProjectRoot())
const localCommands = await getCommands(getProjectRoot())
return uniqBy([...localCommands, ...mcpSkills], 'name')

这一步阻断了“猜中 mcp prompt 名字就可走 SkillTool”的绕行入口。

4.2 validateInput：失败前移到 permission 之前

validateInput() 把大多数错误前置：

const trimmed = skill.trim()
if (!trimmed) return { result: false, message: `Invalid skill format: ${skill}`, errorCode: 1 }

const normalizedCommandName = trimmed.startsWith('/') ? trimmed.substring(1) : trimmed
...
const foundCommand = findCommand(normalizedCommandName, commands)
if (!foundCommand) return { result: false, message: `Unknown skill: ${normalizedCommandName}`, errorCode: 2 }

if (foundCommand.disableModelInvocation) return { result: false, ... errorCode: 4 }
if (foundCommand.type !== 'prompt') return { result: false, ... errorCode: 5 }

remote canonical（_canonical_<slug>）在本地 lookup 前被拦截：

const slug = remoteSkillModules!.stripCanonicalPrefix(normalizedCommandName)
if (slug !== null) {
  const meta = remoteSkillModules!.getDiscoveredRemoteSkill(slug)
  if (!meta) return { result: false, ... errorCode: 6 }
  return { result: true }
}

4.3 checkPermissions：顺序就是策略

判决顺序按代码固定，不是注释约定：

1) deny rules

const denyRules = getRuleByContentsForTool(permissionContext, SkillTool as Tool, 'deny')
for (const [ruleContent, rule] of denyRules.entries()) {
  if (ruleMatches(ruleContent)) {
    return { behavior: 'deny', message: `Skill execution blocked by permission rules`, decisionReason: { type: 'rule', rule } }
  }
}

2) remote canonical auto-allow（但在 deny 之后）

const slug = remoteSkillModules!.stripCanonicalPrefix(commandName)
if (slug !== null) {
  return { behavior: 'allow', updatedInput: { skill, args }, decisionReason: undefined }
}

3) allow rules

const allowRules = getRuleByContentsForTool(permissionContext, SkillTool as Tool, 'allow')
for (const [ruleContent, rule] of allowRules.entries()) {
  if (ruleMatches(ruleContent)) {
    return { behavior: 'allow', updatedInput: { skill, args }, decisionReason: { type: 'rule', rule } }
  }
}

4) safe auto-allow

if (commandObj?.type === 'prompt' && skillHasOnlySafeProperties(commandObj)) {
  return { behavior: 'allow', updatedInput: { skill, args }, decisionReason: undefined }
}

5) ask（并附规则建议）

return {
  behavior: 'ask',
  message: `Execute skill: ${commandName}`,
  suggestions,
  updatedInput: { skill, args },
  metadata: commandObj ? { command: commandObj } : undefined,
}

其中 ruleMatches() 同时处理 exact 与 :* 前缀规则，且统一去掉前导 /，保证 slash 命名与 SkillTool 命名一致：

const normalizedRule = ruleContent.startsWith('/') ? ruleContent.substring(1) : ruleContent
if (normalizedRule === commandName) return true
if (normalizedRule.endsWith(':*')) {
  const prefix = normalizedRule.slice(0, -2)
  return commandName.startsWith(prefix)
}

4.4 call：三条执行路径

call() 的执行顺序：

  1. canonical skill -> executeRemoteSkill
  2. context==='fork' -> executeForkedSkill
  3. 默认 inline -> 复用 processPromptSlashCommand
const slug = remoteSkillModules!.stripCanonicalPrefix(commandName)
if (slug !== null) {
  return executeRemoteSkill(slug, commandName, parentMessage, context)
}
...
if (command?.type === 'prompt' && command.context === 'fork') {
  return executeForkedSkill(...)
}
...
const processedCommand = await processPromptSlashCommand(commandName, args || '', commands, context)
if (!processedCommand.shouldQuery) {
  throw new Error('Command processing failed')
}

这点非常关键：SkillTool inline 路径并不自建 prompt 展开逻辑，而是复用 slash 的 prompt 主链。

4.5 inline 不是“立即执行工具”，而是注入后续上下文

contextModifier() 做的是下一跳上下文补丁：

if (allowedTools.length > 0) {
  const previousGetAppState = modifiedContext.getAppState
  modifiedContext = {
    ...modifiedContext,
    getAppState() {
      const appState = previousGetAppState()
      return {
        ...appState,
        toolPermissionContext: {
          ...appState.toolPermissionContext,
          alwaysAllowRules: {
            ...appState.toolPermissionContext.alwaysAllowRules,
            command: [...new Set([...(appState.toolPermissionContext.alwaysAllowRules.command || []), ...allowedTools])],
          },
        },
      }
    },
  }
}

model/effort 也通过同一 modifier 链注入：

if (model) {
  modifiedContext = {
    ...modifiedContext,
    options: {
      ...modifiedContext.options,
      mainLoopModel: resolveSkillModelOverride(model, ctx.options.mainLoopModel),
    },
  }
}
...
if (effort !== undefined) {
  const previousGetAppState = modifiedContext.getAppState
  modifiedContext = {
    ...modifiedContext,
    getAppState() {
      const appState = previousGetAppState()
      return { ...appState, effortValue: effort }
    },
  }
}

4.6 fork：隔离执行并回收结果

executeForkedSkill() 复用 prepareForkedCommandContext()，走独立 runAgent()：

const { modifiedGetAppState, baseAgent, promptMessages, skillContent } =
  await prepareForkedCommandContext(command, args || '', context)
...
for await (const message of runAgent({
  agentDefinition,
  promptMessages,
  toolUseContext: { ...context, getAppState: modifiedGetAppState },
  canUseTool,
  isAsync: false,
  querySource: 'agent:custom',
  model: command.model as ModelAlias | undefined,
  availableTools: context.options.tools,
  override: { agentId },
})) {
  agentMessages.push(message)
}

结果抽取与收尾：

const resultText = extractResultText(agentMessages, 'Skill execution completed')
...
return { data: { success: true, commandName, status: 'forked', agentId, result: resultText } }
...
finally { clearInvokedSkillsForAgent(agentId) }

4.7 remote canonical：session discovery 驱动

executeRemoteSkill() 先确认 session 已发现，再加载远端 skill 内容：

const meta = getDiscoveredRemoteSkill(slug)
if (!meta) {
  throw new Error(`Remote skill ${slug} was not discovered in this session...`)
}
...
loadResult = await loadRemoteSkill(slug, meta.url)

随后把 frontmatter body 内容注入消息，并做 ${CLAUDE_SKILL_DIR} / ${CLAUDE_SESSION_ID} 替换：

const { content: bodyContent } = parseFrontmatter(content, skillPath)
const skillDir = dirname(skillPath)
...
let finalContent = `Base directory for this skill: ${normalizedDir}\n\n${bodyContent}`
finalContent = finalContent.replace(/\$\{CLAUDE_SKILL_DIR\}/g, normalizedDir)
finalContent = finalContent.replace(/\$\{CLAUDE_SESSION_ID\}/g, getSessionId())

并通过 addInvokedSkill(...) 进入压缩保留状态。

4.8 最终统一成 tool_result

mapToolResultToToolResultBlockParam() 区分 fork 与 inline 文案，但协议一致：

if ('status' in result && result.status === 'forked') {
  return { type: 'tool_result', tool_use_id: toolUseID, content: `Skill "${result.commandName}" completed (forked execution)...` }
}
return { type: 'tool_result', tool_use_id: toolUseID, content: `Launching skill: ${result.commandName}` }

5) Guard / Decision Matrix

5.1 validate / permission guards

Guard 条件 动作 结果
empty-input guard skill.trim()==='' validate fail 立即止损
slash-prefix guard skill 以 / 开头 归一化去前缀 slash/SkillTool 语义一致
remote-discovery guard canonical slug 未发现 validate fail(errorCode 6) 禁止凭空调用远端 skill
unknown-skill guard findCommand miss validate fail(errorCode 2) 不进入 permission
model-invocation guard disableModelInvocation validate fail(errorCode 4) 模型入口硬阻断
prompt-type guard type !== 'prompt' validate fail(errorCode 5) SkillTool 语义收敛
deny-first guard deny rule 命中 behavior:'deny' 显式否决优先
canonical-auto-allow guard canonical slug 命中 allow 系统特例，但晚于 deny
allow-rule guard allow rule 命中 allow 用户显式放行
safe-props guard 仅安全属性 allow 降低 ask 噪音
ask fallback guard 无匹配规则 ask + suggestions 可审计授权闭环

5.2 execution guards

Guard 条件 动作 结果
remote-route guard canonical slug executeRemoteSkill 绕过本地 slash expansion
fork-route guard command.context==='fork' executeForkedSkill 子代理隔离执行
inline-route guard 其他 prompt skill processPromptSlashCommand 与 slash 展开保持一致

6) Failure / Recovery / Degradation

6.1 validate 阶段失败优先

SkillTool 把“不可执行”的状态前置到 validate：

  • 未知/空 skill
  • 非 prompt command
  • disable-model-invocation
  • 未发现 canonical 远端 skill

避免进入 permission 弹窗和执行路径，减少无意义分支。

6.2 deny 的强终态

一旦 deny 命中立即返回，不再继续 allow/safe/canonical 放行分支。终态可解释：

message: `Skill execution blocked by permission rules`

6.3 fork 失败与状态清理

fork 路径使用 finally { clearInvokedSkillsForAgent(agentId) }，即使异常也会清理 skill state，避免跨 agent 污染。

6.4 remote load 失败显式化

executeRemoteSkill() 加载异常直接抛出明确错误，并记录 telemetry，不回退本地命令：

throw new Error(`Failed to load remote skill ${slug}: ${msg}`)

6.5 inline 处理失败不静默

当 processPromptSlashCommand() 返回 shouldQuery=false 时直接抛错：

if (!processedCommand.shouldQuery) {
  throw new Error('Command processing failed')
}

防止半成品 prompt 注入。

7) Invariants

  1. SkillTool 只执行 prompt skill。
  2. disableModelInvocation 必须在 validate 阶段硬阻断。
  3. 权限顺序必须是 deny-first。
  4. remote canonical 可以默认 allow，但必须服从 deny。
  5. inline 和 fork 虽执行语义不同，但都必须回到统一 tool_result 协议。
  6. SkillTool inline prompt 展开必须复用 slash 主链函数，避免双轨实现。

8) Cross-module Contracts

  • 对 01：02 消费 discovery 后 command facts，不重新解释 frontmatter。
  • 对 03：02 是模型平面；03 是用户平面入口。两者共享命令事实源与 prompt 展开核心。
  • 对 04：02 承接来源差异，不把 bundled/plugin/MCP/remote 抹平成同一安全假设。
  • 对 commands.ts：02 依赖其 surface 过滤，不自建第二套 registry。

9) Engineering Constraints / Evolution Guidance

  1. 新增 prompt command 属性时，默认应落入 ask（除非显式加入 SAFE_SKILL_PROPERTIES）；
  2. 不要把 validate 逻辑后移到 call（会增加无意义 permission/execution 路径）；
  3. 不要让 SkillTool 重写一份 prompt expansion 逻辑，必须继续复用 processPromptSlashCommand；
  4. 远端 canonical 扩展必须继续保持“先发现后调用”的 session 语义；
  5. deny-first 顺序是安全底座，变更需有强证据和全链路回归。
