    传输层（SSE / WebSocket / Hybrid）（深潜审计版）

    1) Scope 与 Evidence Boundary

    本页覆盖“链路级可靠性”：SSE/WebSocket/Hybrid transport 的 buffering、flush、replay、reconnect、retry budget 与 close semantics。

    证据范围：

    • src/cli/transports/ccrClient.ts
    • src/cli/transports/HybridTransport.ts
    • src/upstreamproxy/relay.ts
    • 相关 transport 实现（SSE / WebSocket）

    不覆盖：

    • StructuredIO semantic correlation（见 02）；
    • streamed tool queue/backpressure（见 04）；
    • render/UI 投影视图（见 01）。

    2) Core Thesis

    transport 层的职责不是“尽量把包送到”，而是让 delivery retry 与 semantic replay 分离：

    1. buffering/flush 必须保持消息顺序；
    2. reconnect 不能等价于重复语义提交；
    3. retryable 与 permanent failure 要可区分；
    4. close/flush/replay 边界必须可审计。

    3) Runtime State Ownership

    状态类别 所有者 关键函数/字段 说明
    stream accumulator 态 ccrClient.ts createStreamAccumulator / accumulateStreamEvents / clearStreamAccumulatorForMessage stream_event 增量合并与重放
    delayed flush 态 ccrClient.ts + HybridTransport.ts delayed flush timer / buffer 先缓冲后批量写出
    serial uploader 态 HybridTransport.ts SerialBatchEventUploader / write / postOnce HTTP 批量写串行化
    relay framing 态 relay.ts relay packet shaping upstream 到 client 的边界封装
    连接状态机态 各 transport connected/reconnecting/closed 重连预算与终止条件

    4) End-to-end Flow

    1. 上层把消息写入 transport；
    2. stream_event 先进入 accumulator/buffer；
    3. 遇到非 stream_event 或 flush 点时先输出累计 payload；
    4. Hybrid 路径通过串行 uploader 批量 POST；
    5. transport 断线后按 retry budget 进入 reconnect 或 permanent close；
    6. close 前清 timer/buffer，避免 stale replay。

    5) Guard / Decision Matrix

    Guard 条件 动作 结果
    stream_event buffer guard message 是 stream_event 进入 accumulator/buffer 降低碎片化输出
    non-stream flush guard 即将写非 stream_event 先 flush buffered events 保持顺序
    reconnect budget guard 仍在重连预算内 backoff + reconnect 尝试恢复
    permanent failure guard 超预算或不可恢复错误 close 显式终止
    serial write guard Hybrid HTTP 写入 uploader 串行批次发送 防并发写冲突
    close cleanup guard transport close 清 buffer/timer 防 stale replay
    replay guard reconnect/replay 场景 仅重放 buffered delivery state 不重复 semantic state

    6) Failure / Recovery / Degradation

    6.1 短时链路抖动

    • transport 进入 reconnect；
    • 若在预算内成功恢复，则继续 delivery。

    6.2 长时/永久失败

    • 超预算或 permanent failure 后 close；
    • 上层收到明确终止，而非无声挂起。

    6.3 buffer/flush 边界异常

    • close 前统一清理 timer/buffer；
    • 避免 stale stream_event 在下一连接误重放。

    6.4 Hybrid POST 失败

    • 通过批量上传器局部重试或上报失败；
    • 不允许并发写把顺序打乱。

    7) Invariants

    1. close 后不得继续写入旧 transport 实例。
    2. reconnect timer 必须单实例。
    3. buffered stream_event 必须在非 stream 消息前 flush。
    4. replay 只能重放 delivery state，不能重复 semantic commit。
    5. Hybrid 写入必须串行。
    6. 连接终止必须显式可观测。

    8) Cross-module Contracts

    • 对 02：03 提供 delivery reliability，不定义 request ledger 语义。
    • 对 01：03 输出稳定顺序流，01 再将其投影到 UI。
    • 对 04：transport retry 不应让 executor 重复消费同一语义工具事件。
    • 对 relay/proxy：只承载传输 framing，不定义业务重试语义。

    9) Engineering Constraints / Evolution Guidance

    新增 transport 或 replay 逻辑时必须验证：

    1. 是否具备 clear close boundary；
    2. 是否区分 retryable/permanent failure；
    3. 是否会打乱 buffered stream_event 顺序；
    4. 是否把 delivery retry 错写成 semantic replay。

    建议回归：

    • SSE / WS / Hybrid 三分支；
    • delayed flush / close semantics；
    • reconnect success / give-up；
    • Hybrid serial batch upload 失败；
    • accumulator clear/replay 行为。
