Structured I/O 协议与请求关联（深潜审计版）

1) Scope 与 Evidence Boundary

本页覆盖“异步控制平面”与“request-response correlation”：control_request/control_response、keep_alive、cancel、duplicate/orphan/late response、pendingRequests 生命周期。

证据范围：

  • src/cli/structuredIO.ts
  • src/cli/print.ts（control_request/control_response 消费上下文）

不覆盖：

  • transport buffering/replay（见 03）；
  • streamed tool queue/backpressure（见 04）；
  • UI 渲染投影（见 01）。

2) Core Thesis

Structured I/O 的核心价值不是“把 JSON 行发出去”，而是把异步控制平面建模为可验证账本：

  1. 每个 request 必须有唯一生命周期；
  2. cancel 必须先本地收敛，再等待远端迟到响应被吸收；
  3. duplicate/orphan 响应必须被明确识别；
  4. control 与 content 必须共享单一顺序保证。

3) Runtime State Ownership

状态类别 所有者 关键函数/字段 说明
请求账本态 structuredIO.ts pendingRequests 所有未完成请求的唯一主账本
去重态 structuredIO.ts resolvedToolUseIds 重复 tool/control 响应吸收
输出序列态 structuredIO.ts outbound 单一 FIFO 写出队列
请求创建态 structuredIO.ts sendRequest request_id 创建、入队、挂起 promise
响应裁决态 structuredIO.ts processLine / injectControlResponse 解析、命中、resolve/reject
取消态 structuredIO.ts abort handler + control_cancel_request 本地 reject 与远端取消提示

4) End-to-end Flow

  1. 调用方执行 sendRequest，生成 request_id 并写入 outbound；
  2. pendingRequests 记录 promise 与 schema；
  3. 远端回传 control_response，由 processLine 按 request_id 命中；
  4. 命中后 resolve/reject 并清理账本；
  5. 若本地 abort，先 enqueue control_cancel_request，再本地 reject；
  6. 迟到响应由 duplicate/orphan 规则吸收，不再重入业务状态。
// src/cli/structuredIO.ts
private readonly pendingRequests = new Map<string, PendingRequest<unknown>>()
private readonly resolvedToolUseIds = new Set<string>()
readonly outbound = new Stream<StdoutMessage>()

5) Guard / Decision Matrix

Guard 条件 动作 结果
keep_alive guard message.type='keep_alive' 忽略 不污染主账本
env update guard update_environment_variables 更新环境 不进入 request ledger
request register guard 新 request_id 写入 pendingRequests 建立唯一生命周期
duplicate guard toolUseId 已 resolved 丢弃重复响应 防重入
orphan guard 无对应 pending request 忽略或走 unexpected callback 防迟到污染
abort guard signal 触发 enqueue cancel + local reject 先本地收敛
cleanup guard inputClosed reject 所有 pending 防悬挂 promise
output ordering guard 所有写出经 outbound 保持 FIFO 控制/内容顺序一致

6) Failure / Recovery / Degradation

6.1 输入流关闭

  • inputClosed=true 后批量 reject pendingRequests；
  • 防止请求永久等待。

6.2 本地取消竞态

  • abort 时先本地 reject，再向远端发 cancel；
  • 迟到响应由 orphan/duplicate 规则吸收。

6.3 schema/parse 失败

  • processLine 解析或校验失败时 reject 当前 request 并清理账本；
  • 不让坏响应污染后续状态。

6.4 duplicate/late response

  • resolvedToolUseIds 吞掉已完成请求的重复结果；
  • 防 assistant/tool 状态重复落盘。

7) Invariants

  1. 同一 request_id 只允许一次终态。
  2. request 结束后必须从 pendingRequests 删除。
  3. duplicate 响应不得重新注入业务状态。
  4. cancel 后本地状态必须先收敛。
  5. 所有写出必须走单一 outbound 队列。
  6. keep_alive 与 env update 不应污染 request ledger。

8) Cross-module Contracts

  • 对 03：02 定义 semantic correlation，03 只负责 transport delivery。
  • 对 04：tool executor 依赖 02 的 request/response 幂等语义。
  • 对 01：02 输出的控制事件由 render/UI 路径投影，但 UI 不应篡改账本状态。
  • 对 CLI/SDK：StructuredIO 是控制平面事实源，外层只消费其稳定协议。

9) Engineering Constraints / Evolution Guidance

新增 control request 类型时必须验证：

  1. 是否进入 pendingRequests 唯一生命周期；
  2. 是否具备 cancel 与 late-response 吸收语义；
  3. 是否通过 outbound 保持顺序；
  4. 是否会让 duplicate suppression 误伤正常重试。

建议回归：

  • request start/end；
  • keep_alive / env update；
  • duplicate/orphan/late response；
  • local abort vs remote response race；
  • inputClosed 批量 reject。
