Hook 配置注册与匹配器（深潜审计版）

1) Scope 与 Evidence Boundary

本页覆盖“Hook 如何被收集、排序、分组与匹配”，证据范围：

  • src/utils/hooks/hooksConfigSnapshot.ts
  • src/utils/hooks/hooksSettings.ts
  • src/utils/hooks/sessionHooks.ts
  • src/utils/hooks/registerFrontmatterHooks.ts

不覆盖：

  • command/prompt/agent/http 执行器细节（见 02）；
  • permission 决策桥接（见 03）；
  • watcher/progress/session lifecycle UX（见 04）。

2) Core Thesis

配置与 matcher 层的职责不是“把所有 hook 拼起来”，而是把多来源策略收敛为稳定选择语义：

  1. 配置源必须先经过 policy gating；
  2. matcher 排序需可解释且稳定；
  3. session/frontmatter/plugin/builtin 注入不能破坏来源边界；
  4. 无匹配与空 matcher 都必须是显式语义，而不是异常路径。

3) Runtime State Ownership

状态类别 所有者 关键函数 说明
配置快照态 hooksConfigSnapshot.ts captureHooksConfigSnapshot / updateHooksConfigSnapshot / getHooksConfigFromSnapshot settings 快照与刷新
policy gate 态 hooksConfigSnapshot.ts shouldAllowManagedHooksOnly / shouldDisableAllHooksIncludingManaged 控制哪些来源可见
全量 hook 集合态 hooksSettings.ts getAllHooks / getHooksForEvent 多来源汇总
matcher 排序态 hooksSettings.ts sortMatchersByPriority / getSortedMatchersForEvent source priority + matcher 名排序
分组态 hooksSettings.ts groupHooksByEventAndMatcher / getHooksForMatcher event -> matcher -> hooks[]
session 注入态 sessionHooks.ts getSessionHooks / getSessionFunctionHooks / clearSessionHooks 会话期动态 hooks
frontmatter 注入态 registerFrontmatterHooks.ts registerFrontmatterHooks frontmatter hook 注册与事件变换

4) End-to-end Flow

  1. captureHooksConfigSnapshot / updateHooksConfigSnapshot 生成当前有效配置快照；
  2. getAllHooks 汇总 user/project/local/policy + plugin/builtin + session hooks；
  3. groupHooksByEventAndMatcher 构造 event -> matcher -> hooks[] 结构；
  4. sortMatchersByPriority 根据 source priority 与 matcher 名稳定排序；
  5. 执行期 getHooksForEvent / getHooksForMatcher 取出命中集合；
  6. 结果交给统一执行入口。

5) Guard / Decision Matrix

Guard 条件 动作 结果
managed-only guard allowManagedHooksOnly=true 仅保留 managed 来源 收缩可执行面
disable-all guard disableAllHooks=true 返回空配置/跳过后续执行 hooks 全量停用
plugin-only guard restricted to plugin only 屏蔽其它来源 限定策略来源
empty matcher guard event 有 matcher 但 hook 无 matcher 使用 '' key 分组 显式“通配”语义
no-matcher-metadata guard event 不支持 matcher metadata 强制使用空 matcher key 统一分组结构
source-priority guard 来源不同 按 source priority + 字典序排序 稳定匹配顺序
session hook guard sessionId 不存在/已清理 no-op 防跨会话污染
frontmatter stop guard agent-scoped Stop 转换为 SubagentStop 生命周期语义正确

6) Failure / Recovery / Degradation

6.1 配置刷新恢复

  • settings 外部变化后 updateHooksConfigSnapshot 重建快照；
  • 避免长期持有 stale hooks。

6.2 解析/汇总退化

  • 非法/不适用来源在配置阶段被过滤；
  • 匹配阶段以“无匹配”收敛，而不是抛重错。

6.3 session hook 清理退化

  • 删除未知 session 时 no-op；
  • 防止清理路径自身成为故障点。

6.4 frontmatter 注入失败

  • 仅影响局部 frontmatter hook；
  • 不应拖垮全量 registry。

7) Invariants

  1. 所有 HookEvent 必须在分组结构中拥有稳定槽位。
  2. source priority 排序必须稳定可解释。
  3. session hooks 不落盘，只存在于会话态。
  4. 空 matcher 必须是显式分组语义，而非异常。
  5. frontmatter 注入不得破坏原始生命周期事件语义。
  6. 配置快照刷新后，后续执行必须看到新状态。

8) Cross-module Contracts

  • 对 02：01 只负责“选哪些 hook”，不负责“怎么执行”。
  • 对 03：01 输出的命中集合是 permission hook 的输入边界。
  • 对 04：session/frontmatter 注入会影响生命周期 hooks，但不负责 watcher/UX。
  • 对设置系统：01 复用 settings/policy 事实源，不定义第二套配置真值。

9) Engineering Constraints / Evolution Guidance

新增 hook 来源或 matcher 规则时必须验证：

  1. 是否接入 policy gate；
  2. 是否保持 source priority 稳定；
  3. 是否会让 session hooks 泄漏到持久态；
  4. 是否破坏 frontmatter 与 session 注入边界。

建议回归：

  • allowManagedHooksOnly / disableAllHooks / plugin-only 组合；
  • matcher present/absent 与 no-matcher-metadata；
  • source priority 稳定性；
  • session hook add/remove/clear；
  • frontmatter Stop -> SubagentStop 转换。
