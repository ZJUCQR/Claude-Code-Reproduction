    代理循环与工具：回合状态机（深潜审计版）

    2)核心论点

    queryLoop 不是“循环调用模型”，而是一个显式状态重建型自动机：每个 continue 都构造新的 State，每个 return 都携带终止原因。这个设计把复杂恢复流程（withheld 错误、fallback、hook 阻断、token budget 续轮）从“隐式流程”提升为“可审计转移”。

    核心证据（状态定义）：

    // src/query.ts
type State = {
  messages: Message[]
  toolUseContext: ToolUseContext
  autoCompactTracking: AutoCompactTrackingState | undefined
  maxOutputTokensRecoveryCount: number
  hasAttemptedReactiveCompact: boolean
  maxOutputTokensOverride: number | undefined
  pendingToolUseSummary: Promise<ToolUseSummaryMessage | null> | undefined
  stopHookActive: boolean | undefined
  turnCount: number
  transition: Continue | undefined
}

    transition 字段的价值是把“为什么继续”显式写进状态，避免靠日志猜测。

    3)运行时状态所有权

    3.1 () 负责外壳生命周期

    // src/query.ts
export async function* query(params: QueryParams): AsyncGenerator<..., Terminal> {
  const consumedCommandUuids: string[] = []
  const terminal = yield* queryLoop(params, consumedCommandUuids)
  for (const uuid of consumedCommandUuids) {
    notifyCommandLifecycle(uuid, 'completed')
  }
  return terminal
}

    职责： - 承接 queryLoop； - 在正常返回路径统一发 completed 生命周期信号。

    3.2 () 持有唯一主状态

    // src/query.ts
let state: State = {
  messages: params.messages,
  toolUseContext: params.toolUseContext,
  maxOutputTokensOverride: params.maxOutputTokensOverride,
  autoCompactTracking: undefined,
  stopHookActive: undefined,
  maxOutputTokensRecoveryCount: 0,
  hasAttemptedReactiveCompact: false,
  turnCount: 1,
  pendingToolUseSummary: undefined,
  transition: undefined,
}

    职责： - 每轮顶部解构状态； - 每个分支写回完整 next State； - 管理 continue 与 return 的一致语义。

    3.3 追踪状态 ``

    5)守卫与决策矩阵

    分支 条件 动作 结果
    blocking limit 自动压缩禁用且 token 达硬阈值 直接 yield API error return {reason:'blocking_limit'}
    streaming fallback onStreamingFallback 触发 tombstone + 清空数组 + discard executor 同轮重试
    withheld prompt-too-long 413 可恢复错误 暂不 yield，进入恢复链 collapse/reactive compact
    collapse drain retry staged collapse 可提交 写 transition.reason='collapse_drain_retry' continue
    reactive compact retry compact 成功 注入 post-compact messages continue
    max-output escalate cap 实验门满足 maxOutputTokensOverride=64k continue
    max-output recovery 恢复次数 < 上限 注入 meta recovery message continue
    stop_hook_blocking blockingErrors>0 回灌 blocking 错误到 messages continue
    stop_hook_prevented preventContinuation 直接停止 return
    aborted_streaming streaming 阶段 abort drain remaining tool results / 补齐缺失结果 return
    aborted_tools 工具阶段 abort yield interruption + maxTurns 检查 return

    6)失败、恢复与降级

    6.1：先清理旧流，再重建执行器

    if (streamingFallbackOccured) {
  for (const msg of assistantMessages) {
    yield { type: 'tombstone' as const, message: msg }
  }

  assistantMessages.length = 0
  toolResults.length = 0
  toolUseBlocks.length = 0
  needsFollowUp = false

  if (streamingToolExecutor) {
    streamingToolExecutor.discard()
    streamingToolExecutor = new StreamingToolExecutor(
      toolUseContext.options.tools,
      canUseTool,
      toolUseContext,
    )
  }
}

    恢复意义： - 旧流 assistant 变墓碑； - 旧工具结果全部抛弃； - 新 executor 防止旧 tool_use_id 泄漏。

    1) 首先尝试 escalation：

    2) 再走 recovery meta message：

    if (maxOutputTokensRecoveryCount < MAX_OUTPUT_TOKENS_RECOVERY_LIMIT) {
  const recoveryMessage = createUserMessage({
    content:
      `Output token limit hit. Resume directly — no apology, no recap of what you were doing. ` +
      `Pick up mid-thought if that is where the cut happened. Break remaining work into smaller pieces.`,
    isMeta: true,
  })

  state = {
    ...,
    messages: [...messagesForQuery, ...assistantMessages, recoveryMessage],
    maxOutputTokensRecoveryCount: maxOutputTokensRecoveryCount + 1,
    transition: {
      reason: 'max_output_tokens_recovery',
      attempt: maxOutputTokensRecoveryCount + 1,
    },
  }
  continue
}

    3) 仍失败才真正暴露错误。

    6.4：回灌错误并继续

    if (stopHookResult.blockingErrors.length > 0) {
  const next: State = {
    messages: [
      ...messagesForQuery,
      ...assistantMessages,
      ...stopHookResult.blockingErrors,

    toolUseContext,
    autoCompactTracking: tracking,
    maxOutputTokensRecoveryCount: 0,

    maxOutputTokensOverride: undefined,
    pendingToolUseSummary: undefined,

    turnCount,
    transition: { reason: 'stop_hook_blocking' },

    注意这里保留 hasAttemptedReactiveCompact，避免再次压缩形成环路。

    7)不变量

    1. 每次 continue 必须写完整 next State。
    2. turnCount 只在真正进入下一回合 (next_turn) 时增加。
    3. tool_use 必须最终配对 tool_result（真实或合成）。
    4. withheld 错误不可先暴露再恢复。
    5. fallback 时旧流结果必须 tombstone+discard，不得混入新流。
    6. stop hook API error 场景下必须跳过常规 stop hooks 以避免死循环。
    7. queryTracking.depth 每轮递增，保持链路可审计。
    8. 工具阶段 abort 必须先 drain 或补齐结果，再退出回合。

    8)跨模块契约

    • 对 toolExecution.ts：只消费统一 MessageUpdate 语义，不依赖工具内部实现。
    • 对 toolOrchestration.ts / StreamingToolExecutor.ts：允许执行策略替换，但必须维持 tool_use/tool_result 拓扑。
    • 对 stopHooks.ts：接受 preventContinuation 和 blockingErrors 结构化返回；终止决策在 query 层。

    9)工程约束与演进指引

    新增恢复分支时必须同步定义：

    1) transition.reason； 2) 是否推进 turnCount； 3) 是否需要 bypass stop hooks； 4) 是否需要补齐 missing tool_result； 5) 与 hasAttemptedReactiveCompact、maxOutputTokensRecoveryCount 的交互。

    推荐新增分支模板：

    const next: State = {
  messages: ...,
  toolUseContext,
  autoCompactTracking: ...,
  maxOutputTokensRecoveryCount: ...,
  hasAttemptedReactiveCompact: ...,
  maxOutputTokensOverride: ...,
  pendingToolUseSummary: ...,
  stopHookActive: ...,
  turnCount: ...,
  transition: { reason: 'your_new_reason' as const },
}
state = next
continue
