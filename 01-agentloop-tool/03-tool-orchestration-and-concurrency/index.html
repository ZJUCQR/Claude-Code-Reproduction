    代理循环与工具：批处理编排与并发策略（深潜审计版）

    核心论点

    toolOrchestration.ts 的核心不是“并发执行工具”，而是“在保持消息语义稳定的前提下最大化吞吐”：

    • 并发只影响执行时机；
    • 不能影响 context 生效顺序；
    • 不能破坏每个 tool_use_id 的完整生命周期；
    • 判定出错时必须保守降级到串行。

    关键证据：

    function partitionToolCalls(
  toolUseMessages: ToolUseBlock[],
  toolUseContext: ToolUseContext,
): Batch[] {
  return toolUseMessages.reduce((acc: Batch[], toolUse) => {
    const tool = findToolByName(toolUseContext.options.tools, toolUse.name)
    const parsedInput = tool?.inputSchema.safeParse(toolUse.input)
    const isConcurrencySafe = parsedInput?.success
      ? (() => {
          try {
            return Boolean(tool?.isConcurrencySafe(parsedInput.data))
          } catch {
            return false
          }
        })()
      : false
    if (isConcurrencySafe && acc[acc.length - 1]?.isConcurrencySafe) {
      acc[acc.length - 1]!.blocks.push(toolUse)
    } else {
      acc.push({ isConcurrencySafe, blocks: [toolUse] })
    }
    return acc
  }, [])
}

    这里把“安全判定失败 -> 串行”写死为保守策略。

    运行时状态所有权

    持有

    export async function* runTools(...): AsyncGenerator<MessageUpdate, void> {
  let currentContext = toolUseContext
  for (const { isConcurrencySafe, blocks } of partitionToolCalls(...)) {
    ...
  }
}
    • currentContext 是调度层唯一可变上下文引用；
    • 串行分支中实时应用 modifier；
    • 并发分支中延迟应用 modifier。

    `` 持有批次拓扑语义

    职责： - 输入层面判断 isConcurrencySafe； - 将连续安全工具合并为一个并发批； - 将不安全工具切成独占批。

    执行器函数职责分离

    • runToolsSerially：顺序执行 + 即时 context 合并；
    • runToolsConcurrently：并行执行 + 结果流聚合；
    • markToolUseAsComplete：统一清理 in-progress 集合。

    端到端流程

    批次切分

    for (const { isConcurrencySafe, blocks } of partitionToolCalls(...)) {
  if (isConcurrencySafe) {
    ...
  } else {
    ...
  }
}

    并发批执行（先收集 ，再回放）

    const queuedContextModifiers: Record<string, ((context: ToolUseContext) => ToolUseContext)[]> = {}
for await (const update of runToolsConcurrently(...)) {
  if (update.contextModifier) {
    const { toolUseID, modifyContext } = update.contextModifier
    if (!queuedContextModifiers[toolUseID]) {
      queuedContextModifiers[toolUseID] = []
    }
    queuedContextModifiers[toolUseID].push(modifyContext)
  }
  yield {
    message: update.message,
    newContext: currentContext,
  }
}
for (const block of blocks) {
  const modifiers = queuedContextModifiers[block.id]
  if (!modifiers) continue
  for (const modifier of modifiers) {
    currentContext = modifier(currentContext)
  }
}
yield { newContext: currentContext }

    语义：并发期间不直接改全局 context，避免竞态导致顺序漂移。

    串行批执行（即时合并）

    for await (const update of runToolsSerially(...)) {
  if (update.newContext) {
    currentContext = update.newContext
  }
  yield {
    message: update.message,
    newContext: currentContext,
  }
}

    语义：串行路径中上下文变化与消息产出同步推进。

    守卫与决策矩阵

    Guard 条件 动作 结果
    parse fail safeParse 失败 isConcurrencySafe=false 串行降级
    safety fn throw isConcurrencySafe(...) 抛错 返回 false 串行降级
    连续安全工具 当前与前一批都安全 追加到同批 blocks 并发批扩展
    不安全工具到达 当前不安全 新建独占批 顺序屏障
    并发上限 env 未设置或非法 默认 10 限流稳定
    工具完成 runToolUse 结束 markToolUseAsComplete in-progress 清理

    失败、恢复与降级

    安全判定失败时保守降级

    partitionToolCalls 在两类失败都降级串行： - schema parse 失败； - isConcurrencySafe 内部异常。

    这条策略避免“误判为并发安全”导致状态污染。

    单工具错误不击穿调度层

    runToolsSerially/runToolsConcurrently 都依赖 runToolUse 的消息化错误输出；调度层只消费消息，不传播异常为“批次级 crash”。

    -生命周期显式收尾

    toolUseContext.setInProgressToolUseIDs(prev =>
  new Set(prev).add(toolUse.id),
)
...
markToolUseAsComplete(toolUseContext, toolUse.id)

    失败与成功都要执行清理，避免 UI 永久“运行中”。

    不变量

    1. partitionToolCalls 输出的批次顺序必须与输入顺序一致。
    2. 不安全工具必须形成顺序屏障，不得被后续并发工具穿越。
    3. 并发批中 context modifier 只能在批次结束后按原 block 顺序回放。
    4. 每个 toolUseID 都必须 add/remove 成对出现。
    5. runTools 对上游产出的 newContext 必须反映当前可见上下文，不得提前应用并发副作用。
    6. 并发上限必须可控且有默认值。

    跨模块契约

    • 对上游 query.ts：提供统一 AsyncGenerator<MessageUpdate>；query 负责回合推进，不感知批次内部细节。
    • 对下游 toolExecution.ts：只要求 runToolUse 返回消息流与可选 contextModifier。
    • 对工具定义 Tool.ts：并发安全由工具声明，调度器只消费判定，不猜测工具副作用。

    工程约束与演进指引

    新增工具并发能力时必须验证：

    1. isConcurrencySafe 以解析后的输入判断，而非原始对象；
    2. contextModifier 若依赖先后顺序，必须返回“可延迟回放”的纯函数；
    3. 若工具有隐式共享资源（文件锁、进程态、外部会话），默认不并发；
    4. 不要在调度层引入工具特判，除非它是通用语义（例如全局安全门）。

    建议新增并发工具回归用例：

    • 连续 3 个安全工具 + 1 个不安全工具 + 2 个安全工具；
    • 中间工具报错时，前后批次 context 是否可审计；
    • inProgressToolUseIDs 在异常路径是否清零。
